Rookie Coach

A competitive-programming coaching platform that learns from a student's real submission history, identifies recurring weaknesses, and turns those patterns into concrete guidance, practice, and long-term progress tracking.

1. Executive Summary

Rookie Coach is intended to become a full competitive-programming guidance system built around the student's own evidence. Instead of asking a beginner to remember and describe their weaknesses, the system should inspect a longitudinal history of submissions, failed attempts, accepted solutions, problem difficulty, contest context, and code changes to discover patterns the student may not notice independently.

The browser extension is primarily the data-collection layer. Its purpose is to help the student import their own competitive-programming history, with explicit permission, from supported platforms such as Codeforces, AtCoder, CodeChef, LeetCode, and potentially others. The real product is the coaching system built on top of the collected history.

Working thesis: personalized feedback becomes more useful when it is grounded in the student's actual attempts and recurring mistakes rather than generic topic lists or generic AI advice.

2. The Problem

A typical beginner watches tutorials, follows a bootcamp or roadmap, solves some easy problems, and starts entering contests. Their rating can improve before their fundamentals become consistent. They may know several techniques superficially while repeatedly making the same implementation mistakes, misunderstanding edge cases, choosing poor approaches, or avoiding unfamiliar topics.

Existing competitive-programming platforms retain pieces of this history, but the student usually sees it as a sequence of isolated submissions. Rookie Coach should turn that fragmented history into a structured learning loop.

Fragmented evidence

Attempts are spread across multiple platforms, contests, problem archives, and accounts.

Weak reflection

Students often move to the next problem without systematically reviewing why previous attempts failed.

Generic practice

A random problem list cannot automatically explain which weaknesses a specific student needs to address.

3. Product Vision

The long-term product should feel more like a persistent competitive-programming mentor than a one-shot chatbot. It should remember what the student has struggled with, recognize repeated patterns, explain those patterns in understandable language, and change its recommendations as the student's skills evolve.

Candidate coaching capabilities

  • Detect recurring implementation mistakes across many submissions.
  • Identify topics that appear missing, weak, or inconsistently applied.
  • Compare failed and accepted attempts for the same problem.
  • Generate post-contest reviews based on the student's actual decisions.
  • Recommend the next problems for a reason that can be explained to the student.
  • Track whether previously identified weaknesses are improving.
  • Build a personalized learning plan that adapts over time.
These are product directions, not finalized requirements. The first version should deliberately solve one narrow coaching problem well.

5. Data Collection Layer

The initial concept uses a Chrome extension installed by the student. With explicit permission, the extension would collect the student's own submissions and source code where the platform technically allows access and where the chosen integration approach is compatible with applicable platform rules.

1. Student installs extension
2. Student links a platform account
3. Extension collects authorized history
4. Data is normalized into a common format
5. Coaching pipeline analyzes the history

6. Analysis and Coaching Layer

A useful architecture should separate facts that can be extracted reliably from code and metadata from higher-level interpretation. The system should not rely on an LLM to invent facts that deterministic analysis can calculate directly.

Deterministic signals

  • Verdict frequency
  • Attempt counts
  • Time between attempts
  • Language/template usage
  • Submission diffs
  • Difficulty progression

Program analysis

  • AST-level structure
  • Complexity indicators
  • Common bug patterns
  • Suspicious constructs
  • Algorithmic-pattern recognition
  • Implementation-style drift

LLM-assisted interpretation

  • Explain findings in plain language
  • Summarize contest performance
  • Connect code patterns to concepts
  • Generate study guidance
  • Produce reflection questions
  • Write personalized reports
Design principle: extract first, reason second, generate last. Structured evidence should exist before a model is asked to interpret it.

8. Privacy, Consent, and Security

Competitive-programming source code can be personal academic work, and browser extensions operate in a security-sensitive environment. Data ownership and consent therefore need to be part of the product architecture from the beginning.

  • Collect only data the student explicitly authorizes.
  • Explain which platforms, pages, and data categories the extension accesses.
  • Request the minimum browser permissions necessary.
  • Provide a clear way to disconnect accounts and delete imported data.
  • Avoid collecting platform passwords.
  • Handle cookies, session tokens, or other authentication material only when strictly necessary and with a deliberate security design.
  • Keep secrets out of the browser bundle and out of the Git repository.
  • Clearly distinguish data that stays local from data uploaded to a hosted service.
  • Document retention, deletion, and export behavior.
A local-first default could become a major trust advantage for an open-source project, but it remains a product and architecture decision to validate rather than assume.

9. MVP Strategy

The first version should prove one complete learning loop. Supporting every platform and every kind of coaching at once would make it difficult to tell whether the core idea actually works.

A useful first end-to-end loop

  1. Support one competitive-programming platform.
  2. Import a real student's historical submissions.
  3. Normalize accepted and failed attempts.
  4. Analyze one or two categories of recurring weakness.
  5. Produce a coaching report backed by specific evidence.
  6. Give the student a small set of next actions or practice problems.
  7. Measure whether the student considers the diagnosis accurate and useful.

Candidate first coaching outcomes

10. Candidate Roadmap

Phase 0 — Discovery

  • Select the first platform.
  • Select the first measurable coaching outcome.
  • Verify the platform's actual data-access path.
  • Define local-versus-hosted data boundaries.

Phase 1 — Collection prototype

  • Create the extension skeleton.
  • Link one user account.
  • Import and normalize submission history.
  • Store data safely.

Phase 2 — Coaching prototype

  • Implement the first analysis pipeline.
  • Generate evidence-backed findings.
  • Create a student-facing report.
  • Test with a small university cohort.

Phase 3 — Hosted product

  • Deploy services on Railway or another chosen platform.
  • Add user accounts if required.
  • Add additional competitive-programming platforms.
  • Explore a sustainable monetization model.

11. Evaluation for the University Project

The university version should include a defensible evaluation method. Rating change alone is noisy and may require too much time, so the project can measure several shorter-term indicators of coaching quality.

  • Diagnosis agreement: do students recognize the weaknesses identified by the system?
  • Actionability: do students know what to practice after reading the report?
  • Repeated-error reduction: do previously identified mistake categories appear less often?
  • Practice efficiency: do students need fewer failed attempts on related problems?
  • Retention: can students solve related problems later without the same type of hint?
  • Qualitative usefulness: do students consider the system more useful than a generic problem recommendation list?

12. Open Source, Hosting, and Business Direction

The project is intended to be open source so that anyone can download it, inspect the code, and run it locally. At the same time, a hosted version may be deployed on Railway to provide a lower-friction option for students who do not want to self-host.

Open-source version

  • Transparent data handling
  • Community contributions
  • University collaboration
  • Local/private use
  • Reproducible research and demos

Potential hosted version

  • No local setup required
  • Managed analysis infrastructure
  • Cross-device history
  • Potential premium features
  • Possible subscription model
Monetization is intentionally undecided. The immediate priority is proving that the data pipeline and coaching loop are useful before deciding what should be paid, hosted, or free.

13. High-Impact Open Questions

  1. First outcome: after collecting a student's history, what is the single most valuable thing version 1 should do?
  2. First platform: which platform should be supported completely before adding another?
  3. Historical depth: must version 1 import all past submissions, or can it begin from recent history?
  4. Data scope: source code only, or source + verdicts + problem metadata + contest context + problem statements?
  5. Storage: should source code stay local by default, upload only after opt-in, or use another model?
  6. Identity linking: how should a student prove ownership of handles across multiple platforms?
  7. Analysis split: what belongs in deterministic/static analysis and what genuinely benefits from an LLM?
  8. Evaluation: what measurable result will demonstrate that the university project succeeded?
  9. Open-source license: which license should be selected?
  10. Hosted differentiation: if a paid hosted version exists later, what does it add beyond the open-source version?

14. Collaboration and Fresh-Chat Handoff

The GitHub repository should be the durable source of truth for this project. The goal is to make it possible to continue development from a second account, a fresh chat, or another development environment without depending on the original conversation history.

What a new collaborator or fresh chat should know immediately

  • The browser extension is the collection layer, not the entire product.
  • The core ambition is a long-term personalized competitive-programming coach.
  • The system should learn from actual submission history, including mistakes, not only accepted solutions.
  • The project should remain open source and runnable locally.
  • A hosted Railway deployment is a future option, not a current architectural requirement.
  • Do not silently convert unresolved ideas into fixed requirements.
  • Major product and architecture decisions should be recorded in the repository.

Immediate next work

Choose the first supported platform and the first measurable coaching outcome. Then perform a focused technical investigation of that platform's current submission-history and source-code access path before building a large multi-platform architecture.

Project principle: collect only what the student authorizes, preserve useful evidence, and make every important coaching recommendation explainable in terms of that evidence.
