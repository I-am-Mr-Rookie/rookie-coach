1. Executive Summary

Rookie Coach is intended to become a full competitive-programming guidance system built around the student's own evidence. Instead of asking a beginner to remember and describe their weaknesses, the system should inspect a longitudinal history of submissions, failed attempts, accepted solutions, problem difficulty, contest context, and code changes to discover patterns the student may not notice independently.

The browser extension is primarily the data-collection layer. Its purpose is to help the student import their own competitive-programming history, with explicit permission, from supported platforms such as Codeforces, AtCoder, CodeChef, LeetCode, and potentially others. The real product is the coaching system built on top of the collected history.

Working thesis: personalized feedback becomes more useful when it is grounded in the student's actual attempts and recurring mistakes rather than generic topic lists or generic AI advice.
Execution model: development is designed around autonomous, repository-driven runs. Each run has a hard 30-minute wall-clock cap and must leave a durable handoff so the project owner does not have to babysit coding agents.

2. Autonomous Agent Run System

This section is the operational contract for AI coding agents working on Rookie Coach. It is intentionally explicit enough for a weaker model to follow without a human continuously supervising it. A run is one bounded unit of autonomous work that starts by reading the repository state, performs one small task, verifies the result, records what changed, and leaves the repository in a resumable state.

Hard limit: no run may exceed 30 minutes of wall-clock time. At minute 27 the agent must stop starting new implementation work and begin checkpointing. At minute 30 it must stop, even if the task is unfinished. An unfinished but well-documented checkpoint is acceptable; an unbounded run is not.
No-babysitting rule: the human is not the run orchestrator. Do not ask “what should I do next?”, “should I continue?”, “which library do you prefer?”, or similar routine implementation questions. Read the repository, choose the highest-priority safe task that fits the timebox, make reversible low-risk decisions, test them, and document assumptions. Ask the human only for a genuine human-only blocker.

2.1 Definition of a run

Every run must satisfy all of the following:

  • It has one primary objective, not a collection of unrelated goals.
  • The objective is small enough to reach a useful checkpoint in at most 30 minutes.
  • It begins by inspecting the current repository state; it never assumes a clean tree or assumes previous agents finished correctly.
  • It defines acceptance criteria before editing code.
  • It performs the smallest useful implementation or investigation that advances the current milestone.
  • It runs targeted verification before claiming success.
  • It updates persistent project state so a fresh model can resume without the previous conversation.
  • It ends in one of the explicit terminal states: DONE, PARTIAL_CHECKPOINT, BLOCKED, or RESEARCH_COMPLETE.

2.2 Mandatory wall-clock budget

Elapsed timePhaseRequired behavior
0–2 minBoot / recover contextInspect git state, read agent contract, state, backlog, recent decisions, and any existing run log. Do not edit yet.
2–5 minSelect / size taskChoose one READY task. Write 1–3 acceptance checks. If the task cannot fit, split it before starting.
5–21 minExecuteImplement or investigate only the selected slice. Prefer focused changes over broad rewrites.
21–26 minVerifyRun the smallest relevant tests, lint, typecheck, parser checks, or fixture comparisons. Fix only issues caused by the run.
26–27 minDecision pointIf verification is still failing, stop feature work. Decide whether the safest outcome is a checkpoint or blocker record.
27–30 minCheckpoint / handoffUpdate state and run log, inspect the final diff, commit/push when authorized and appropriate, then stop.

The phase boundaries are intentionally conservative. Finishing early is good. Never use the final three minutes to begin “one more small fix.”

2.3 How an agent must measure the timebox

At the first shell/tool step, record a start timestamp. Check elapsed time at each phase transition and after any slow command. In a POSIX shell, a model may use the following pattern if the environment does not provide a run timer: 

RUN_STARTED_EPOCH=$(date -u +%s)
# ...work...
NOW_EPOCH=$(date -u +%s)
ELAPSED_SECONDS=$((NOW_EPOCH - RUN_STARTED_EPOCH))
# 1620s = minute 27: stop new work and checkpoint
# 1800s = minute 30: hard stop

A single command must not consume the entire run. Never start watch mode, an interactive development server, or an indefinite process during an autonomous run. Put explicit timeouts around commands that might hang. As a default, cap ordinary commands at 8 minutes; an install/build/test may use up to 12 minutes only when necessary and only if enough run time remains for cleanup and handoff. If a command times out, inspect the failure once; do not blindly rerun it.

2.6 Task selection algorithm

A fresh model must follow this exact order rather than improvising:

  1. Run git status --short. Preserve existing human or agent changes; never discard them just to get a clean tree.
  2. Read AGENTS.md, docs/PROJECT_STATE.md, the top of docs/BACKLOG.md, and the most recent entries in docs/RUN_LOG.md and docs/DECISIONS.md.
  3. If another run left an unfinished but coherent checkpoint, resume it only if its next step fits the current run.
  4. Otherwise choose the highest-priority READY task whose dependencies are satisfied.
  5. If that task is obviously larger than about 20 minutes of implementation plus verification, split it into smaller backlog tasks before coding and take only the first slice.
  6. If no READY task exists, derive the smallest safe task from the current milestone and add it to the backlog. Do not invent a new product milestone.
  7. State the selected task and acceptance checks in the run log or temporary scratch note, then execute.

2.7 No-babysitting decision policy

When ordinary implementation details are ambiguous, the agent should not interrupt the user. Use the following deterministic fallback order:

  1. Follow existing repository precedent. Reuse the current language, framework, package manager, naming, test style, and directory conventions.
  2. Prefer the smallest reversible change. Add a narrow adapter/function/fixture instead of a generalized framework unless the backlog explicitly requires generalization.
  3. Prefer boring dependencies. Use existing dependencies first, then standard-library capabilities, then a mature small dependency only when it materially reduces risk.
  4. Preserve privacy and data safety. When unsure whether data should leave the device, keep it local and document the unresolved choice.
  5. Preserve behavior. If requirements are unclear, do not remove, rename, migrate, or rewrite working surfaces without a recorded reason.
  6. Record assumptions. A reversible assumption belongs in the run log; a durable architectural choice belongs in the decision log.
Human-only blocker criteria. A run may ask the user for input only when progress genuinely requires something the agent cannot safely infer or obtain: credentials/authorization, spending money or enabling paid infrastructure, destructive or irreversible operations, legal/terms approval, a product-policy choice that changes the promised behavior, or access to an external resource controlled only by the user. Routine library choices, filenames, code style, test organization, refactors, and other reversible technical details are not human-only blockers.

2.8 Editing rules

  • Never rewrite unrelated files “for cleanup” during a focused run.
  • Never delete or reset unknown uncommitted work. Inspect it and work around it.
  • Do not perform a broad dependency upgrade as a side effect of adding one feature.
  • Do not regenerate lockfiles unless the selected task requires a dependency change.
  • Do not make mass formatting changes unless formatting is the actual task.
  • Do not hide failures by weakening tests, disabling type checks, swallowing exceptions, or removing validation.
  • Do not claim an external API or website supports a capability unless it was verified from authoritative evidence or a reproducible fixture.
  • For platform scraping/collection experiments, prefer recorded fixtures and deterministic parsers before live automation.
  • Never put secrets, session tokens, cookies, credentials, private source histories, or user data into Git.

2.9 Verification ladder

Verification should match the change. A weaker model must not either skip tests entirely or waste the run on an unrelated full-suite test. Use the cheapest applicable checks first and escalate only while time remains:

  1. Syntax / parse check for edited files.
  2. Targeted unit or fixture test for the changed behavior.
  3. Relevant package-level lint/typecheck.
  4. Relevant package test suite.
  5. Repository-wide build/test only when the change is cross-cutting or the project is small enough to finish safely inside the run.

If a pre-existing failure is discovered, distinguish it from a regression caused by the run. Do not spend the rest of the time fixing unrelated failures. Record the exact command and a short failure summary in PROJECT_STATE.md or the run log.

2.10 Terminal states and what to do at minute 27

StateUse whenRequired end-of-run actions
DONEAll acceptance checks passed.Update state/backlog/run log, inspect diff, commit and push if authorized, then stop.
PARTIAL_CHECKPOINTUseful coherent progress exists but the whole task is not complete.Make the code safe, describe exactly what works and what remains, split the remaining work into a READY task, checkpoint if repository policy permits, then stop.
BLOCKEDA genuine human-only or external blocker prevents progress.Record the blocker, evidence, and the single smallest piece of information/action needed. Do not keep asking variants of the same question.

2.11 Commit and synchronization behavior

  • Before committing, inspect git diff and git status --short.
  • Commit only coherent work. A checkpoint commit is allowed when it is safe and clearly labeled, but never label known-broken work as complete.
  • Use concise task-oriented commit messages, for example feat(adapter): parse submission fixture or docs(run): record RC-012 checkpoint.
  • If authenticated GitHub access is available and project policy allows it, push the commit so the repository remains the collaboration source of truth.
  • If pushing is unavailable, do not stall the run. Leave a clean local commit when possible and record the commit hash plus exact push command in the run log.
  • Never force-push, rewrite public history, delete branches, or modify repository visibility during an ordinary run.

2.12 Research runs

Platform-access research also uses the 30-minute limit. The agent should answer one narrow question per run, such as “What submission metadata can the official Codeforces API return today?” or “Can a logged-in user obtain their own source text through the normal website flow?” Research runs must prefer authoritative platform documentation and reproducible observations, record the date, separate confirmed facts from assumptions, and produce a concrete next task. A research run must not silently become a two-hour browsing session.

2.13 Debugging runs

Debugging is also bounded. Create or identify a reproducible failure, form one hypothesis at a time, and spend no more than about 12 minutes pursuing a single hypothesis. If the root cause remains unknown near the checkpoint boundary, preserve the reproducer, logs, commands, and eliminated hypotheses for the next run. “Still debugging” is not a reason to cross 30 minutes.

2.14 Minimum end-of-run handoff

Every run log entry should be understandable by a model that has never seen the previous chat. Use this exact compact structure:

## Run YYYY-MM-DD / RC-XXX
Status: DONE | PARTIAL_CHECKPOINT | BLOCKED | RESEARCH_COMPLETE
Objective: one sentence

Changed:
- file/path — what changed and why

Verified:
- command — PASS/FAIL, short result

Assumptions / decisions:
- only non-obvious items

Remaining / next:
- one concrete next task, ideally with backlog ID

Blocker (only if blocked):

2.17 First-run bootstrap behavior

If an agent receives a repository that has only this overview and no operational state files, Run 1 is already decided. The agent must not ask the human what to build first, which platform to choose, which product outcome to prioritize, or how to structure the agent process. It must execute RC-001 from the fixed run queue below. The bootstrap must create AGENTS.md, docs/PROJECT_STATE.md, docs/BACKLOG.md, docs/DECISIONS.md, and docs/RUN_LOG.md; copy the hard constraints from this document; seed RC-002 through RC-012 exactly as described below; verify the files; checkpoint/commit when authorized; and stop within 30 minutes.

Runs 1–12 have enough product context already. Do not stop to ask the owner an open-ended product question during these runs. The decisions and temporary defaults below are the authorized execution context. If a later permanent choice is still undecided, use the stated temporary default, keep the implementation reversible, record it, and continue.

2.20 Deterministic branching rules for unexpected findings

  • If Codeforces official API lacks source code: this is expected to be handled as a capability gap, not a project blocker. Continue metadata work; use the verified normal browser/user-export route for source experiments only when legitimate; preserve explicit source-status.
  • If live source collection is ambiguous under platform rules: do not ask the owner to authorize a bypass. Stay on fixture/user-export parsing and record the live path as deferred.
  • If a proposed dependency/framework choice is unclear: use the current stack defaults above or existing repository precedent. Do not ask the owner.
  • If the repository already contains partially implemented equivalents: inspect them, map them to the closest RC task, preserve compatible work, and adapt the acceptance criteria rather than duplicating files.
  • If a task finishes early: verify and checkpoint early. Do not opportunistically start the next run's task in the same run unless it is a tiny documentation correction required by the current acceptance criteria.
  • If a task does not fit: create a narrower child task, checkpoint, and stop. The 30-minute cap wins over completing the numbered item in one sitting.
  • If web/tool access is temporarily unavailable: finish any deterministic repository work possible, record the external blocker precisely, and stop. Do not ask open-ended product questions as a substitute.
Autonomy target: a capable or weaker coding model should be able to receive only this repository plus the instruction Do Run 1, execute RC-001 without clarification, and leave a state from which another fresh model can execute RC-002. The same handoff pattern should continue through RC-012 without routine owner supervision.

3. The Problem

A typical beginner watches tutorials, follows a bootcamp or roadmap, solves some easy problems, and starts entering contests. Their rating can improve before their fundamentals become consistent. They may know several techniques superficially while repeatedly making the same implementation mistakes, misunderstanding edge cases, choosing poor approaches, or avoiding unfamiliar topics.

Existing competitive-programming platforms retain pieces of this history, but the student usually sees it as a sequence of isolated submissions. Rookie Coach should turn that fragmented history into a structured learning loop.

Fragmented evidence

Attempts are spread across multiple platforms, contests, problem archives, and accounts.

Weak reflection

Students often move to the next problem without systematically reviewing why previous attempts failed.

Generic practice

A random problem list cannot automatically explain which weaknesses a specific student needs to address.

4. Product Vision

The long-term product should feel more like a persistent competitive-programming mentor than a one-shot chatbot. It should remember what the student has struggled with, recognize repeated patterns, explain those patterns in understandable language, and change its recommendations as the student's skills evolve.

Candidate coaching capabilities

  • Detect recurring implementation mistakes across many submissions.
  • Identify topics that appear missing, weak, or inconsistently applied.
  • Compare failed and accepted attempts for the same problem.
  • Generate post-contest reviews based on the student's actual decisions.
  • Recommend the next problems for a reason that can be explained to the student.
  • Track whether previously identified weaknesses are improving.
  • Build a personalized learning plan that adapts over time.
These are product directions, not finalized requirements. The first version should deliberately solve one narrow coaching problem well.

7. Analysis and Coaching Layer

A useful architecture should separate facts that can be extracted reliably from code and metadata from higher-level interpretation. The system should not rely on an LLM to invent facts that deterministic analysis can calculate directly.

Deterministic signals

  • Verdict frequency
  • Attempt counts
  • Time between attempts
  • Language/template usage
  • Submission diffs
  • Difficulty progression

Program analysis

  • AST-level structure
  • Complexity indicators
  • Common bug patterns
  • Suspicious constructs
  • Algorithmic-pattern recognition
  • Implementation-style drift

LLM-assisted interpretation

  • Explain findings in plain language
  • Summarize contest performance
  • Connect code patterns to concepts
  • Generate study guidance
  • Produce reflection questions
  • Write personalized reports
Design principle: extract first, reason second, generate last. Structured evidence should exist before a model is asked to interpret it.

9. Privacy, Consent, and Security

Competitive-programming source code can be personal academic work, and browser extensions operate in a security-sensitive environment. Data ownership and consent therefore need to be part of the product architecture from the beginning.

  • Collect only data the student explicitly authorizes.
  • Explain which platforms, pages, and data categories the extension accesses.
  • Request the minimum browser permissions necessary.
  • Provide a clear way to disconnect accounts and delete imported data.
  • Avoid collecting platform passwords.
  • Handle cookies, session tokens, or other authentication material only when strictly necessary and with a deliberate security design.
  • Keep secrets out of the browser bundle and out of the Git repository.
  • Clearly distinguish data that stays local from data uploaded to a hosted service.
  • Document retention, deletion, and export behavior.
A local-first default could become a major trust advantage for an open-source project, but it remains a product and architecture decision to validate rather than assume.

10. MVP Strategy

The first version should prove one complete learning loop. Supporting every platform and every kind of coaching at once would make it difficult to tell whether the core idea actually works.

A useful first end-to-end loop

  1. Support one competitive-programming platform.
  2. Import a real student's historical submissions.
  3. Normalize accepted and failed attempts.
  4. Analyze one or two categories of recurring weakness.
  5. Produce a coaching report backed by specific evidence.
  6. Give the student a small set of next actions or practice problems.
  7. Measure whether the student considers the diagnosis accurate and useful.

Candidate first coaching outcomes

OutcomeWhy it fits the projectMain challenge
Recurring mistake diagnosisDirectly exploits failed attempts and source-code history.Findings must be accurate enough that students trust them.
Topic-gap detectionEasy to explain and useful for planning practice.Must infer more than what problem tags already say.
Next-problem recommendationCreates a continuous coaching loop.Recommendations need clear personalization logic.
Contest reviewNaturally bounded and easy to demonstrate.Needs enough timing and attempt context to explain decisions.

12. Candidate Evaluation Measures

The independent project should use an evaluation method appropriate to its current stage; the five-volunteer pilot is informal product feedback. Rating change alone is noisy and may require too much time, so the project can measure several shorter-term indicators of coaching quality.

  • Diagnosis agreement: do students recognize the weaknesses identified by the system?
  • Actionability: do students know what to practice after reading the report?
  • Repeated-error reduction: do previously identified mistake categories appear less often?
  • Practice efficiency: do students need fewer failed attempts on related problems?
  • Retention: can students solve related problems later without the same type of hint?
  • Qualitative usefulness: do students consider the system more useful than a generic problem recommendation list?
